### 7.1. Автоматическая проверка качества кода
Как только вы загружаете решение в формате zip-файла (и только zip-файла!), автоматически запускается проверка качества кода. Без её прохождения решение не будет учтено.

**Как правильно упаковать решение в zip:**
* Упаковывайте только исходный код решения.
* Не добавляйте объёмные файлы — датасеты, дампы, архивы, медиа, скомпилированные бинарники.
* Не упаковывайте build-директории и зависимости, например:
  * `node_modules`, `.venv`, `venv`, `env` — каталоги зависимостей;
  * `target`, `build`, `dist`, `out`, `bin`, `obj` — каталоги сборки;
  * `.git`, `.idea`, `__pycache__`, `coverage` — служебные каталоги.
* Один архив в формате `.zip` разумного размера, с исходным кодом в корне или в понятной структуре.

> **Совет:** чем чище и легче архив, тем быстрее и надёжнее проходит проверка. Лишние каталоги зависимостей и сборки не нужны — проверяется именно ваш исходный код.

## Приложение A. Контракт API «/process»
Единый контракт, который команды-участники должны реализовать на своём сервисе. Проверяющая система обращается к этому эндпоинту для нагрузочного тестирования.

**Схема запроса/ответа**
```http
POST /process
Content-Type: application/json

{
  "payload": "<строка>",
  "payload_id": "<идентификатор>"
}
```

**Response (200 OK)**

```json
{
  "result": "<строка>"
}
```

**Логика (одинакова для всех):**

* Эндпоинт один — обрабатывает и маскирование, и демаскирование.
* Направление определяется по `payload_id` — используйте его как ключ корреляции «маскирование → демаскирование».
* Первый запрос с новым `payload_id` — маскирование (`payload` = исходная строка) → верните маску и запомните соответствие.
* Второй запрос с тем же `payload_id` — демаскирование (`payload` = ваша маска) → верните исходную строку.
* Ответ всегда: `{"result": "..."}`.

## Приложение B. Инструкция по нагрузочному тестированию

Ваш сервис проверяется системой нагрузочного тестирования: она подаёт нагрузку по эталонному датасету и оценивает точность маскирования и демаскирования. Условия одинаковы для всех команд.

### Что нужно реализовать

* Один HTTP-эндпоинт `POST /process` по контракту из Приложения A.
* Сервис можно развернуть на http или https (в т.ч. с самоподписанным сертификатом) — проверка идёт с `ssl_verify=false`, ошибок сертификата не будет.

### Логика проверки (пошагово)

Проверка идёт по каждому элементу датасета парой запросов с одним `payload_id`:

1. **Прямая проверка (маскирование).** Система шлёт исходную строку с новым `payload_id` → ваш сервис возвращает маску и запоминает соответствие. Результат сравнивается с эталонной маской (метрика — нормированное span-based расстояние Левенштейна, [0..1]).
2. **Обратная проверка (демаскирование).** Система шлёт вашу же маску с тем же `payload_id` → ваш сервис возвращает исходную строку. Результат сравнивается с исходной строкой из датасета.

Проверяются категории ПД из ТЗ (ФИО, даты, паспорт, гражданство, орган выдачи, код подразделения, в/у, адрес, email, телефон, ИНН, номер карты, CVV, ПИН, имя держателя и сложные предложения).

### Требования к надёжности (обязательно учесть)

* **Таймаут** одного запроса — 10 секунд. Ответ дольше считается неответом.
* **Ретраи** — до 2 на каждый запрос (итого до 3 попыток). Делайте эндпоинт идемпотентным по `payload_id`.
* **429 (Too Many Requests)** допустим под нагрузкой: система применит ожидание и ретраи (учитывается `Retry-After`). Если 429 сохраняется — это значимый результат (решение не держит нагрузку) и попадёт в метрики.
  * Если 429 не проходит на маскировании — демаскирование по этому элементу не запрашивается; если на демаскировании — учитывается, и проверка продолжается.
* **Стоп при недоступности:** после 5 невалидных запросов подряд прогон останавливается (429 невалидным не считается и счётчик не сбрасывает; успешный ответ сбрасывает счётчик).
* **Нагрузка:** по умолчанию прогон идёт по всем категориям ~5 минут с целевым RPS 1000; элементы датасета переиспользуются. Целевое значение latency — не более 1 с (ориентир, не жёсткий лимит).

### Чек-лист «как пройти успешно»

- [ ]  Реализован `POST /process` строго по контракту (`{payload, payload_id}` → `{result}`).
- [ ]  Маскирование сохраняет соответствие по `payload_id`; повторный запрос с тем же id возвращает исходную строку.
- [ ]  Ответ отдаётся быстро и стабильно под нагрузкой (RPS 1000+).
- [ ]  Эндпоинт идемпотентен (безопасен к ретраям), корректно возвращает 429 при перегрузке.
- [ ]  Сервис доступен по указанному URL (http или https) на момент прогона.
